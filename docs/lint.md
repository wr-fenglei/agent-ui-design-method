# 检查排版和交付

从 1× PNG 测量, 坐标从左上角起算, Python 3.9 或以上可运行, 检查在本地执行

| 什么时候 | 运行什么 | 能知道什么 |
|---|---|---|
| 有第一张可读的整屏 | `python3 tools/design_density.py first.png --json` | 标出疑似把内容拉散的空带、重复横线及所在位置 |
| 首稿有多个状态 | `python3 tools/design_lint.py spec.json --layout-only` | 对清单里每张状态图执行同一套排版检查 |
| 准备交付 | `python3 tools/design_lint.py spec.json --json` | 在实际图片和设计规范上做下表的全部检查, 有错误返回 1 |

首稿的清单只需写 `{"states":{"review":{"screen":"first.png"}}}`, 完整设计根据[模板](../tools/design-system.template.json)填写, 路径相对于清单, 将参考选择、初稿的排版决定、检查结果和修订写在同目录的 `process.md`

| 检查 | 它如何工作 |
|---|---|
| 空白与分割线 | 按内容区分析 1× 屏幕, 输出可回到原图查看的空带或线段位置, 重点看同组信息和连续行, 只有外观明确的情形才报错 |
| 设计规格与操作 | 读取 JSON 中的字号、行高、间距、边界、图标和状态关系, 核对状态导出, 用主控件的默认和交互态像素检查可见变化 |
| 按钮对齐 | 从单色按钮底面找出文字和图标, 测量它们的纵向中心, 达到 4 px 偏移时报错, 提供同排按钮框还会测上下错位 |
| 界面色和作品 | 从所选案例和本稿的实际像素核对界面色, 扫描作品外的绿色, 含可替换图片的状态再导出一张只换作品的画面, 换图后的框内须有可见图案, 框外必须逐像素一致 |
| 文字对比 | 每一状态取文字和邻近底色, 常规文字至少 4.5:1, 大字至少 3:1, 提供 Figma 文字层后还会在字形边界内逐个检查, 报告列出实测值和需用原图核对的文字 |

**排版怎样判定** 工具在同一片平坦底色上量可见文字之间的空带, 和它前后两处间距比较, 也检查有独立底面的容器是否只有少量内容却留下大块内边距, 它会找到无内容的双横线, 以及连续的长横线是否只隔开几个短字段, 行内有多列可比较数据的表格另行识别

用上一份退稿回查, 左栏一段上下净空为 67 px, 相邻间距为 16 和 27 px, 右栏 4 条 782 px 横线隔开 3 行短字段, 用同一程序检查三个参考整屏均未报错, 渐变玻璃上无法辨认平坦区域时, 从原图核对该区域的间距, 照片留白、画布外沿和固定工具区也需要结合用途判断

确有状态切换需要预留空间时, 在该状态的 `layoutExceptions` 数组记录报告中的 `rule`、`box`, 再写 `reason` 和 `evidenceState`, 程序会比较引用状态的同位置是否真的出现相应内容, 经实际换图证明属于作品的线条也会单列

Figma 稿在能调用 Plugin API 的环境加载[文字层导出工具](../tools/export_text_layers.js), 执行 `await exportTextLayers(figma, {review: "待审画板ID", done: "结果画板ID"})`, 将返回值保存为 `text-layers.json`, 在清单顶层写 `"textLayers":"text-layers.json"`

参考图按所选示例的目录直接打开, 读者可从制作记录了解作者选择了哪些组件, lint 读取可测的排版结果, 组件是否适合当前任务仍需回到整屏判断

维护检查器时, 用 `python3 -B -m unittest discover -s tools -p 'test_*.py'` 运行 Python 正反例, 用 `node --test tools/test_export_text_layers.js` 检查 Figma 文字导出器
